PART 1: WHAT IS THE PROBLEM? (Explain this first to professor)
================================================================

Imagine an employee at DRDO takes a photo of a classified missile
blueprint. He cannot email the PDF directly — security will catch it.

So instead, he opens a normal-looking JPG photo of a cricket match.
He uses free software to HIDE the blueprint data inside that photo's
pixels. The photo still looks 100% normal to human eyes. He emails
it out. Antivirus does not catch it. Firewall does not catch it.
He walks out with classified data.

This technique is called STEGANOGRAPHY — hiding secret data inside
innocent image files.

YOUR PROJECT builds the detector that catches this.

Real-world example of how hiding works:
  - Normal pixel value  = 200  (colour value, 0-255 range)
  - Attacker changes it = 201  (last bit changed = 1 bit of data)
  - Human eye sees ZERO difference
  - But across millions of pixels = you can hide a whole document
  - This specific method is called LSB (Least Significant Bit) hiding

PART 2: WHY EXISTING TOOLS FAIL (Your Research Gap)
================================================================

Tool            Problem
-----------     -----------------------------------------------
Xu-Net          Only checks pixel layer. Fooled if attacker
                uses JPEG frequency hiding instead of LSB.

Yedroudj-Net    Fails when image is resized or JPEG-compressed
                after hiding. Cannot generalise well.

Antivirus       Completely blind to steganography. Not designed
                for this problem at all.

Gap Summary:
No single existing tool checks ALL hiding methods at the same time.
That is your research gap. That is what you are solving.


================================================================
PART 3: YOUR SOLUTION — THREE-INSPECTOR SYSTEM
================================================================

Think of your model like a THREE-INSPECTOR TEAM checking the
same image simultaneously:

INSPECTOR A — Pixel Branch (Branch A)
  - Looks directly at raw pixel values
  - Uses SRM filters to amplify tiny bit-level changes
  - Catches: LSB steganography
  - Analogy: Like a pixel-level microscope
  - Implemented as: CNN on pixel residual maps

INSPECTOR B — Frequency Branch (Branch B)
  - Converts the image into frequency domain (DCT)
  - Same math that JPEG compression uses
  - Catches: JPEG-domain / DCT steganography
  - Analogy: Like an X-ray scanner for image frequencies
  - Implemented as: CNN on DCT coefficient maps

INSPECTOR C — Statistics Branch (Branch C)
  - Checks statistical patterns of the image
  - Does the histogram look natural? Is chi-square test normal?
  - Catches: GAN-based steganography (AI-generated stego)
  - Analogy: Like a financial auditor checking for anomalies
  - Implemented as: Simple MLP on handcrafted stat features

SENIOR INSPECTOR — Fusion Layer
  - Gets all three branch outputs (feature vectors)
  - Combines them using Dense layers + Softmax
  - Gives final verdict: CLEAN or STEGO
  - Also gives a confidence percentage (e.g. 94.7% stego)

No existing single tool does all three together.
That combination is your innovation.

PART 5: INNOVATION 2 — DEFENSE CONTEXT SCORING
================================================================

Not just "stego or not" — gives RISK SCORE based on:

  Factor                  How it raises risk
  -----------------       ------------------------------------
  Who sent the file?      Low-privilege user = higher risk
  What time?              2:30 AM file transfer = suspicious
  File size anomaly?      5MB PNG where 500KB expected = flag
  Where is it going?      External IP destination = red alert

Example output to security officer:
  "Image is 94.7% likely STEGO. Sent by intern account at 2:18 AM
   to external IP 103.x.x.x. Risk Level: CRITICAL"

This is actionable intelligence, not just a yes/no answer.


================================================================
PART 6: INNOVATION 3 — CPU-ONLY DEPLOYMENT
================================================================

Problem with existing models:
  - Xu-Net, Yedroudj-Net, modern steganalysis tools
  - All need a GPU server to run
  - DRDO endpoints are AIR-GAPPED machines (no internet, no GPU)

Your solution:
  - After training on GPU (Google Colab is free)
  - Apply INT8 quantization to the trained model weights
  - Model size reduces 4x, inference speed increases
  - Runs on a normal CPU laptop
  - Accuracy drop is minimal (usually less than 2%)

This makes your model practically deployable in defense infrastructure.
That is a real engineering contribution.

PART 8: DATASET
================================================================

You will use publicly available research datasets:

BOSS Dataset (Break Our Steganographic System):
  - Standard benchmark used in all steganalysis research
  - 10,000 grayscale images, 512x512 pixels
  - You embed hidden data in 5,000 of them (stego class)
  - Keep 5,000 as original (clean class)
  - 50-50 split is important — prevents class imbalance

DIV2K Dataset:
  - High-quality colour images
  - Good for testing generalisation

You create the stego images yourself:
  - Write a simple LSB embedder in Python (about 20 lines)
  - Embed random data into half the dataset images
  - Now you have labelled train/test data

PART 13: RISKS AND HOW TO HANDLE THEM
================================================================

Risk 1: Training loss not decreasing
  Fix: Check your data pipeline first. Label leakage (clean images
       accidentally getting stego label) is the #1 cause.
       Print 10 samples, verify manually.

Risk 2: Running out of time in Month 3
  Fix: Branch C and Streamlit demo are optional. If time is tight,
       ship the two-branch model with good evaluation graphs.
       A working two-branch model is better than three broken ones.

Risk 3: Dataset too large for your laptop
  Fix: Start with 2,000 images (1,000 stego + 1,000 clean) for
       Month 1. Scale to full dataset in Month 2 on Colab.

Risk 4: Both students doing same work
  Fix: Use GitHub. Each student works on their own branch (Git
       branch). Merge only after testing. Clear ownership per module.

Risk 5: Report piling up at end
  Fix: Write one section per week from Week 8. Introduction and
       literature review can be written during Month 1 itself.
